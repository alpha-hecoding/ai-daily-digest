## 二、Agent 架构与范式

### 2.1 Agent Harness 成为研究热点：三篇论文同时聚焦

本日 arXiv 上出现了三篇直接研究 Agent Harness 设计的论文，这标志着 AI Agent 研究正在从"模型能力"转向"工程化落地"。

#### 论文 1：Harness Design for Coding Agents（arXiv:2609.20804）

**研究方法**

研究团队构建了一个轻量级编码 harness，固定执行循环，变化三个核心组件：
- **规划（Planning）**：是否提供任务分解
- **动作空间（Action Space）**：预定义工具 vs 纯 Bash
- **上下文管理（Context Management）**：5 种策略 × 4 种窗口预算

在 SWE-Bench Verified 和 Terminal-Bench 2.1 上评估 4 个模型、176 个匹配设置。

**核心发现**

| 发现 | 详情 |
|---|---|
| 上下文管理 | 窗口越紧张越有价值，主要收益来自防止上下文溢出失败 |
| 最佳策略 | 规则省略 → LLM 摘要（先规则后模型）效率最高 |
| 规划的作用 | 对弱模型是准确性支架，对强模型是成本节省 |
| 动作空间 | Bash 能力强的模型用纯 Bash 接口成本更低 |

**💡 对你的价值**

如果你在构建编码 Agent，这篇论文给出了明确的工程指导：
1. **上下文管理是第一优先级**——先做好上下文压缩和溢出防护
2. **先规则后模型**——用正则/规则先过滤，再让 LLM 做摘要
3. **按模型能力选接口**——强模型给 Bash 就够了，弱模型需要预定义工具

---

#### 论文 2：SoL-Pi — 递归扩展自动研究循环（arXiv:2609.20519）

**核心问题**

编码 Agent 从"有监督的代码补全"走向"无人值守的全天候探索"时，token 效率成为扩展递归自我改进的关键瓶颈。

**解决方案**

NVIDIA 团队提出 SoL-Pi，通过 4 个机制实现 token 效率提升：

| 机制 | 功能 |
|---|---|
| 动作执行优化 | 减少冗余动作 |
| 上下文压缩 | 智能压缩历史上下文 |
| 观察处理 | 优化观察结果的处理方式 |
| 委托阅读 | 将阅读任务委托给更高效的组件 |

**实验结果**

在 EdgeBench 51 个任务的评估中：

| 指标 | 改进 |
|---|---|
| Token 流量 | 减少 44.7-49.0% |
| API 成本 | 降低约 1/3 |
| 每小时节省 | $8.75-$13.50（vs 原生 Codex/Claude Code） |
| 性能 | 与 Pi 持平（GPT-5.6 Sol 和 Opus 5） |

**💡 对你的价值**

SoL-Pi 直接解决了编码 Agent 的成本问题。如果你在用 Claude Code 或 Codex 做自动化开发，每小时 $8-13 的节省在长时间运行场景下非常可观。代码已在 GitHub 开源（NVlabs/SoL-Pi），值得集成到你的 Agent 工作流中。

#### 论文 3：How Do Agent Harnesses Create Value?（arXiv:2609.20474）

**研究方法**

在 Retail（2 个实验）和 Airline（τ²-bench 试点）中研究 Agent Harness 的价值来源。核心对比：
- **Fixed**：预写的任务特定计划
- **Sham**：打乱的策略文本（字数匹配）

在 265 个匹配单元中隔离规划内容的贡献。

**核心发现**

| 发现 | 数据 |
|---|---|
| 规划的价值 | Fixed 比 Sham 提高 7.17 个百分点成功率 |
| 收益集中 | 高复杂度任务收益最大 |
| 验证器效果 | 只读终端验证器拒绝 61% 无效 episode |
| 误杀率 | 验证器扣留 17% 正确 episode |
| 额外成本 | 每 episode 不到 1 美分 |

**关键洞察**

哪个组件更重要取决于错误接受的代价：
- **低责任场景**：规划收益占主导
- **高责任场景**：验证器避免的误通过占主导
- **性价比之选**：独立验证器能以极低成本捕获几乎全部的误通过收益

**💡 对你的价值**

如果你的 Agent 需要处理高风险任务（如金融交易、医疗建议），验证器比规划更重要。一个只读的结果验证器每 episode 成本不到 1 美分，但能拦截 61% 的错误结果——这是目前性价比最高的 Agent 安全方案。

### 2.2 RAFT：有状态 RAG 用于故障排除 Agent

**论文**：arXiv:2609.20754（EMNLP 2026 Industry Track）

**核心问题**

企业客户支持中的故障排除 Agent 需要从历史案例中检索可操作的指导，但现有 RAG 系统将支持案例视为静态文档，忽略了它们的多阶段、有状态特性。

**解决方案**

RAFT（Retrieval-Augmented Framework for Troubleshooting Agents）将每个已关闭的历史案例抽象为时间线条目的有向链，在条目级别进行检索：

```
历史案例 → 时间线条目链 → 条目级检索 → 匹配中间状态 → 返回锚定轨迹
```

**实验结果**

- 在案例进展的每个阶段，RAFT 的 Case Hit 都优于 vanilla RAG 和 GraphRAG
- 在 Apache Jira 真实数据上提供了方向性证据，优势可迁移到真实案例

**💡 对你的价值**

如果你在构建客服/运维类 Agent，RAFT 的"有状态 RAG"思路非常值得借鉴。传统的 RAG 把文档当成扁平的文本块，但故障排除天然是多步骤、有状态的——用户的问题可能处于故障排查的某个中间阶段，需要匹配的是"同样处于这个阶段的历史案例"，而不是"最相似的文档"。

### 2.3 Chronicle：LLM Agent 回归测试新范式

**论文**：arXiv:2609.20625

**核心问题**

LLM 的响应是非确定性的，Agent 中的失败难以复现：失败依赖于不可位级复现的推理、读取变化状态的工具、以及重新运行很少重复的多步轨迹。

**解决方案**

Chronicle 在 Agent 运行的非确定性边界记录为不可变信封，然后从记录中重放。核心操作是**切点重放（cut-point replay）**：

| 操作 | 说明 |
|---|---|
| 记录 | 在非确定性边界捕获为不可变信封 |
| 全重放 | 从记录重放所有边界，零模型调用 |
| 切点重放 | 选择部分边界从记录服务，其余用新代码实时执行 |

**实验结果**

| 指标 | 数据 |
|---|---|
| 记录开销 | 每次交叉 23μs（占 300ms 模型调用的 0.008%） |
| 全重放 | 零模型调用，20 次重复位级稳定 |
| 突变测试 | 切点测试捕获所有让不安全操作通过的突变体 |
| 基线对比 | 全 stub 基线使用相同断言，一个都抓不到 |

**💡 对你的价值**

如果你在生产环境部署了 LLM Agent，回归测试是一个真实痛点。Chronicle 的方案非常优雅——不需要复现 LLM 的非确定性，而是在边界记录结果，然后用切点重放测试代码变更。这让你可以把 Agent 的故障案例变成 CI 中的回归测试，确保修复不会回退。代码已在 GitHub 开源（theagentplane/chronicle）。

### 2.4 RetireOPD：自退休在策略蒸馏

**论文**：arXiv:2609.20784

**核心问题**

用 RL 训练的多轮 Agent 每条轨迹只收到一个标量奖励，自策略蒸馏（OPD）通过特权教师的 token 级监督提供密集信号。但两个问题破坏了这一方案：
1. 特权信息本身不能让教师可靠
2. 教师监督的收益是阶段依赖的

**解决方案**

RetireOPD 采用**自适应退休（Adaptive Retirement）**：
1. 先用环境奖励优化解耦的技能条件教师
2. 用 RL + OPD 联合训练无技能学生
3. 学生自行判断何时放弃教师——当差异不再缩小且达到教师成功率的目标比例时
4. 之后仅用 RL 继续训练

**实验结果**

在 Qwen2.5 1.5B-7B 模型上：

| 基准 | 改进 |
|---|---|
| ALFWorld 成功率 | +14.1% 至 +18.8% |
| WebShop 准确率 | +11.8% 至 +19.0% |
| 超越教师 | 在所有设置中都超过技能条件教师 |

**💡 对你的价值**

RetireOPD 的"自适应退休"思路可以推广到更广泛的 Agent 训练场景。核心洞察是：教师不是越久越好，学生应该自己判断何时"毕业"。这避免了预定义蒸馏日程的僵化，让训练过程更加自适应。

## 四、AI 工具与技巧

### 4.1 编码 Agent 成本优化指南

基于 SoL-Pi 和 Harness Design 论文的研究结果，以下是编码 Agent 成本优化的具体建议：

#### 策略 1：上下文管理优先

```
优先级排序：
1. 上下文溢出防护（最重要）
2. 规则省略 → LLM 摘要（先规则后模型）
3. 让省略内容可恢复（收益不大，可跳过）
```

**具体操作**：
- 设置上下文窗口硬限制，超出时自动截断
- 用正则表达式先过滤无关内容（如日志时间戳、重复警告）
- 再用 LLM 对剩余内容做摘要

#### 策略 2：按模型能力选接口

| 模型能力 | 推荐接口 | 原因 |
|---|---|---|
| Bash 能力强 | 纯 Bash 接口 | 成本更低，灵活度更高 |
| Bash 能力弱 | 预定义工具 | 避免 Bash 错误导致的重试成本 |

|---|---|---|

| 强模型 | 省略规划 | 节省成本，准确性不变 |

## 五、值得深读的研究

### 5.1 dQwen3.5：混合注意力扩散语言模型

**论文**：arXiv:2609.20751

**研究方法**

将预训练的自回归（AR）模型适配为扩散语言模型（DLM）是一种成本高效的路径。但几乎所有此类适配都从全注意力 Transformer 开始，而 AR 建模已转向混合架构（交错注意力和 RNN 层）。

问题在于：RNN 是结构因果的，难以双向化。

研究团队调查了这类骨干网能否成为有效的 DLM，通过适配 Qwen3.5（0.8B、2B、4B、9B），产出 dQwen3.5 系列。

**核心发现**

| 发现 | 详情 |
|---|---|
| 训练效率 | 混合骨干网在全注意力控制的约一半 token 达到给定训练损失 |
| 解码行为 | 跨尺度表现出任意顺序解码行为 |
| 并行解码 | 在并行解码下表现强劲 |

**启发**

1. **混合架构不是 DLM 的障碍**：虽然 RNN 层是因果的，但通过适当的适配，混合架构仍然可以成为有效的扩散语言模型起点
2. **训练效率翻倍**：这意味着用相同的计算预算，可以训练更大或更好的模型
3. **并行解码的潜力**：扩散语言模型天然支持并行解码，可能在未来挑战自回归范式的主导地位

**💡 对你的价值**

扩散语言模型是"后自回归时代"的重要候选架构。dQwen3.5 证明了现有混合注意力模型可以通过低成本适配变成 DLM——这意味着你现有的 AR 模型资产不会浪费。关注这个方向，它可能在未来 1-2 年内改变 LLM 的推理方式。

### 5.2 语言模型组高估共识

**论文**：arXiv:2609.20538

**研究方法**

在推理任务上重放人类审议，研究语言模型组的行为。37 页论文，包含预注册和完整代码数据。

**核心发现**

语言模型组在重放人类审议时**高估了共识程度**——模型组倾向于表现出比实际人类群体更高的一致性。

**启发**

1. **多 Agent 系统的隐患**：如果你用多个 LLM Agent 组成"委员会"做决策，它们可能比预期更趋同
2. **多样性不足**：模型组可能缺少真正的人类审议中的观点多样性
3. **设计建议**：在多 Agent 系统中需要显式引入多样性机制（如不同 prompt、不同模型、不同温度）

**💡 对你的价值**

如果你在用多 Agent 系统做决策（如圆桌讨论、代码审查），这篇论文提醒你：模型组可能看起来达成了共识，但实际上只是"群体思维"。解决方案：
- 为不同 Agent 设置不同的系统提示/视角
- 使用不同模型（如一个用 Claude，一个用 GPT）
- 显式要求每个 Agent 提出反对意见

### 5.3 Refuse, Decompose, Refresh：闭环 AI 评估的声明安全协议

**论文**：arXiv:2609.20538

**研究方法**

提出一个三步协议，确保 AI 评估的声明是安全的：

| 步骤 | 动作 | 说明 |
|---|---|---|
| Refuse | 拒绝 | 当缺乏干净的参考流或匹配的运行时比较时， abstain |
| Decompose | 分解 | 分别报告协议执行、操作误准入和结构假设，而非单一 PASS/FAIL |
| Refresh | 刷新 | 将分布偏移警报视为失效和重算参考图的请求，而非故障证据 |

**核心发现**

在 24 个策略组件、3 种需求机制、2 种故障掩码族的聚合模拟器中：
- 72 个机制-组件单元中仅 55 个被参考准入
- 55 个中 54 个保持运行时准入
- 稳定误准入为 0/20（95% 单侧上限 0.1391）

**启发**

1. **评估可以是可复现的但仍然支持错误的声明**：这是闭环系统中的核心风险
2. **"null"必须是参考相对的**：干净的故障空流在不同机制下触发不同的警报
3. **可执行合约**：将可观察支持、统计校准和合理声明链接起来

**💡 对你的价值**

如果你在构建 AI 评估系统或基准测试，这篇论文提供了一个严谨的框架。核心洞察：**可复现 ≠ 正确**。你需要确保评估系统不仅在技术上是可复现的，而且在统计上是校准的，并且声明的范围不超出证据的支持范围。

### 5.5 Harm Laundering in GPT Models

**论文**：arXiv:2609.20779（EMNLP 2026 主会）

**核心发现**

GPT 模型中的性别歧视在安全训练的生成过程中被**转化而非减少**——歧视从一种形式变成了另一种形式，而非被真正消除。

**💡 对你的价值**

这篇论文对 AI 安全研究有重要意义。它揭示了安全训练的局限性：模型可能学会了"隐藏"偏见而非"消除"偏见。对于依赖 LLM 做内容审核或公平性判断的应用，需要意识到模型本身可能只是将偏见"洗白"了。
