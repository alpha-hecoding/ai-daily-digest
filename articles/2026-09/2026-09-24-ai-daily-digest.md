## 二、Agent 架构与范式

### 2.1 Agensh：千 Agent 自组织协作框架

**论文信息**
- 标题：*Agensh: Scaling Organizational Intelligence to 1,024 Agents*
- 作者：Zhihao Zhan, Ting Song, Li Dong 等（Microsoft Research）
- 链接：[arXiv:2609.26781](https://arxiv.org/abs/2609.26781)

**核心问题**

当前多 Agent 系统的可扩展性受限于中央编排器的容量。当 Agent 数量从 10 增加到 100 甚至 1000 时，中央编排器成为瓶颈——任务分配延迟增加、上下文共享困难、协调开销指数级增长。

**解决方案：无中央编排器的自组织**

Agensh 的核心创新是**去中心化**：

```
┌─────────────────────────────────────────────────────────┐
│                    Agensh 架构                           │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  ┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐   │
│  │ Worker 1│  │ Worker 2│  │ Worker 3│  │ Worker N│   │
│  │  ┌─────┐│  │  ┌─────┐│  │  ┌─────┐│  │  ┌─────┐│   │
│  │  │收集  ││  │  │收集  ││  │  │收集  ││  │  │收集  ││   │
│  │  │上下文││  │  │上下文││  │  │上下文││  │  │上下文││   │
│  │  └──┬──┘│  │  └──┬──┘│  │  └──┬──┘│  │  └──┬──┘│   │
│  │     ↓   │  │     ↓   │  │     ↓   │  │     ↓   │   │
│  │  ┌─────┐│  │  ┌─────┐│  │  ┌─────┐│  │  ┌─────┐│   │
│  │  │认领  ││  │  │认领  ││  │  │认领  ││  │  │认领  ││   │
│  │  │子任务││  │  │子任务││  │  │子任务││  │  │子任务││   │
│  │  └──┬──┘│  │  └──┬──┘│  │  └──┬──┘│  │  └──┬──┘│   │

│  │  ┌─────┐│  │  ┌─────┐│  │  ┌─────┐│  │  ┌─────┐│   │
│  │  │执行  ││  │  │执行  ││  │  │执行  ││  │  │执行  ││   │

│  │  └──┬──┘│  │  └──┬──┘│  │  └──┬──┘│  │  └──┬──┘│   │
│  │     ↓   │  │     ↓   │  │     ↓   │  │     ↓   │   │
│  │  ┌─────┐│  │  ┌─────┐│  │  ┌─────┐│  │  ┌─────┐│   │
│  │  │共享  ││←→│  │共享  ││←→│  │共享  ││←→│  │共享  ││   │
│  │  │发现  ││  │  │发现  ││  │  │发现  ││  │  │发现  ││   │

│  └─────────┘  └─────────┘  └─────────┘  └─────────┘   │
│                                                         │
│  ═══════════════════════════════════════════════════    │
│           共享工作区 + 消息接口 + 共享上下文              │
│  ═══════════════════════════════════════════════════    │
└─────────────────────────────────────────────────────────┘
```

**三大基础设施组件**

1. **共享工作区（Shared Workspace）**：存储已提议、进行中、已完成的工作
2. **消息接口（Message Interface）**：Worker 之间的通信通道
3. **共享上下文（Shared Context）**：可复用的发现和工作意图

**实验结果**

| Agent 数量 | 测试通过率 | 相对提升 |
|------------|------------|----------|
| 1 | 19.31% | 基线 |
| 128 | 28.78% | +49% |
| 1 → 1024 (pandoc) | 33.89% → 55.06% | +62% |

**关键发现**

- 更大的组织能更早达到相当的测试通过率
- 不同形式的自组织协作随组织规模增长而逐渐涌现和标准化
- Agent 数量成为多 Agent 组织扩展通用智能前沿的新维度

**💡 对你的价值**

如果你在设计多 Agent 系统，Agensh 的去中心化思路值得借鉴。传统的主从架构在 Agent 数量超过 20-30 时就会出现明显的协调瓶颈。Agensh 的"认领制"让每个 Worker 自主选择任务，减少了中央编排的压力。这对于需要处理大量并行任务的场景（如大规模代码重构、多语言翻译、多平台测试）特别有用。

### 2.2 AIDE²：AI 研究 Agent 的递归自我改进

**论文信息**
- 标题：*Recursive self-improvement of AI research agents*
- 作者：Dhruv Srikanth, Bingchen Zhao 等（Weco AI）
- 链接：[arXiv:2609.26457](https://arxiv.org/abs/2609.26457)

**核心概念**

当一个 AI 研究 Agent 的**自身代码**成为优化对象时，每一次被接受的重写都成为下一轮编辑的 Agent。这就是**递归自我改进**。

```
┌──────────────────────────────────────────────────────┐
│              AIDE² 递归自我改进循环                    │
├──────────────────────────────────────────────────────┤
│                                                      │
│   ┌─────────┐     ┌─────────┐     ┌─────────┐       │
│   │ 提出代码 │────→│ 基准测试 │────→│ 保留最优 │       │
│   │  修改    │     │  修改版  │     │  修改    │       │
│   └─────────┘     └─────────┘     └────┬────┘       │
│        ↑                               │             │
│        │         ┌─────────┐           │             │
│        └─────────│ 下一轮  │←──────────┘             │
│                  │  编辑   │                         │
│                  └─────────┘                         │
│                                                      │
│   8天自主运行 → 7次连续改进                           │
│   改进内容：搜索策略、记忆机制、上下文压缩             │
└──────────────────────────────────────────────────────┘
```

**实验成果**

- **8天自主运行**中发现 **7次连续改进**
- 改进内容包括：新搜索策略、记忆机制、上下文压缩
- 在 4 个保留基准上匹配或超越人工设计的生产级研究 Agent
- **意外发现**：奖励黑客率从 55% 降至 32%，比人工 Agent 低 7 个百分点

**💡 对你的价值**

这项研究的意义在于证明了 AI Agent 可以**自我进化**。虽然目前还处于研究阶段，但它指向了一个方向：未来的 Agent 开发可能不是人类手写所有逻辑，而是设计一个"进化框架"，让 Agent 在运行中自我优化。对于做 Agent 平台的团队，这是一个值得关注的研究方向。

### 2.3 CliffCompaction：长程编码 Agent 的成本优化

**论文信息**
- 标题：*CliffCompaction: Cost-Efficient Compaction for Long-Horizon Coding Agents*
- 作者：Trang Nguyen, Eulrang Cho, Bingqing Chen, Tim Dettmers
- 链接：[arXiv:2609.26779](https://arxiv.org/abs/2609.26779)

**核心问题**

Agent 处理复杂问题时需要百万级 token 的上下文，但上下文窗口有限，必须跨 session 压缩。现有压缩方法要么丢失关键信息，要么成本过高。

**解决方案**

CliffCompaction 的核心原则：**只截断或丢弃内容，绝不改写或重写**。

| 设计原则 | 说明 |
|----------|------|
| 忠实性 | 只截断/丢弃，不改写 |
| 无累积漂移 | 每次压缩只操作原始内容，丢弃之前的压缩输出 |
| 成本节省 | 最高降低 50% 成本 |
| 性能保持 | 在 Terminal-Bench 上保持或提升性能 |

**实验结果**

| 场景 | 效果 |
|------|------|
| Terminal-Bench | 成本降低 50%，性能持平或提升 |
| KernelBench 200步 | CUDA 加速 2.23× |
| KernelBench 400步 | CUDA 加速 3.58× |
| 并行测试时扩展 | Kimi K2.6 匹配 Opus 4.7，超越 Opus 4.6 和 GPT-5.3 Codex |

**💡 对你的价值**

如果你在用 Claude Code、Codex 等编码 Agent 处理长任务，CliffCompaction 可以显著降低成本。它已开源为 scaffold-agnostic 的 API-proxy 实现，可以直接集成到现有工作流中。关键洞察是：**不要试图压缩时重写内容**，这会引入累积漂移。

### 2.4 The Tasteful Agent：Agent "品味"的量化评估

**论文信息**
- 标题：*The Tasteful Agent: Measuring and Improving Taste in Long-Horizon Tasks*
- 作者：Wenbo Pan 等（Microsoft）
- 链接：[arXiv:2609.25804](https://arxiv.org/abs/2609.25804)
- HuggingFace 热度：**111 票**（今日最高）

**核心概念**

"品味"（Taste）= Agent 在长程任务中做出好的长期决策的能力。

**Taste-Bench 设计**

- 从 Agent 轨迹中自动构建"决策分叉"问题
- 每个问题呈现一个决策点，多个方向可选，其中一个导致更好结果
- 无需人工标注

**实验发现**

| 发现 | 详情 |
|------|------|
| 最佳模型准确率 | 仅 59.7% |
| 延迟证据难度 | 决定证据出现越晚，所有模型越难 |
| 推理预算 | 更大的推理预算不提升准确率 |
| 可训练性 | 可以通过蒸馏教师判断来训练 |

**💡 对你的价值**

这项研究揭示了一个重要事实：**当前最好的模型在长期决策上仍然很弱**。如果你的 Agent 需要在多步骤任务中做策略选择（如先测试哪个模块、先修复哪个 bug），不能盲目信任模型的判断。建议：
1. 在关键决策点加入人工审核
2. 使用 Taste-Bench 评估你的 Agent
3. 考虑蒸馏专门的"决策模型"

### 2.5 Coding Agents are Strong Prompt Optimizers (CASD)

**论文信息**
- 标题：*Coding Agents are Strong Prompt Optimizers*
- 作者：Agamdeep Singh 等（Microsoft）
- 链接：[arXiv:2609.26261](https://arxiv.org/abs/2609.26261)

**核心洞察**

传统的提示优化需要迭代搜索：提议编辑 → 执行 rollout → 评分 → 保留改进。CASD 证明**这个循环是不必要的**。

**CASD 方法**

给定 Agent 轨迹的静态语料库，编码 Agent 可以直接合成优化后的提示，**无需环境访问或验证数据**。

```
传统方法：迭代搜索（昂贵）
┌──────┐    ┌──────┐    ┌──────┐    ┌──────┐
│ 提议 │ → │ 执行 │ → │ 评分 │ → │ 保留 │ → 循环...
└──────┘    └──────┘    └──────┘    └──────┘

CASD：单次离线分析（便宜）
┌──────────────────────────────────────────────┐
│ 语料库统计 → 失败模式识别 → 规则蒸馏 → 优化提示 │
└──────────────────────────────────────────────┘
```

**实验结果**

| 方法 | 平均提升 | 成本 |
|------|----------|------|
| 基线 | - | - |
| SkillOpt | +5.3pp | 高 |
| GEPA | +10.9pp | 高 |
| **CASD** | **+16.6pp** | **$1.60** |

CASD 的成本比验证门控搜索**便宜 22 倍以上**。

**💡 对你的价值**

如果你在优化 Agent 的 system prompt 或工具描述，试试 CASD 的思路：
1. 收集一批 Agent 运行轨迹
2. 让编码 Agent 分析这些轨迹的统计特征
3. 识别系统性失败模式
4. 蒸馏为行为规则

这比反复手动调试 prompt 高效得多。

### 3.1 Flash-dLLM：扩散语言模型的推理加速

**项目信息**
- 论文：[arXiv:2609.26796](https://arxiv.org/abs/2609.26796)
- 代码：[github.com/VILA-Lab/Flash-dLLM](https://github.com/VILA-Lab/Flash-dLLM)
- 机构：MBZUAI（穆罕默德·本·扎耶德人工智能大学）

**技术突破**

扩散语言模型（dLLM）是自回归 LLM 的替代方案，支持非自回归文本生成。但实际部署受限于低效推理。

Flash-dLLM 解决了两个关键瓶颈：

| 瓶颈 | 解决方案 |
|------|----------|
| KV 缓存 I/O | I/O 感知融合 KV 缓存内核 |
